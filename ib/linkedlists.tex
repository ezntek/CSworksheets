\subsection{Re-evaluating Arrays as a data structure}

In order to understand the properties, advantages and disadvantages of linked lists, we must re-evaluate how arrays work. Take this array
in Java as an example:

\begin{minted}{java}
int[] nums = {3, 4, 5, 6};
\end{minted}

the array \emph{\texttt{nums}} stores multiple numbers in the same variable by placing them next to each other in memory. For example:

\begin{figure}[htbp]
    \centering
    \begin{tikzpicture}
        \foreach \i/\v in {0/3,1/4,2/5,3/6} {
            \pgfmathsetmacro\x{\i*1.5}
            \draw[thick] (\x,0) rectangle (\x+1.5,1);
            \node[anchor=south] at (\x+0.75,1.1) {\mono \small \i};
            \node[orange] at (\x+0.75, 0.5) {\monobold{\v}};
        }
        \draw[gray,thick,->] (0.6, -0.6) -| (0,-0.1);
        \node[gray,anchor=west] at (0.7, -0.6) {\mono \small Address 4000: \emph{nums}};
    \end{tikzpicture}
    \caption{the array in the above code block in memory}
    \label{fig:array}
\end{figure}

Since the items of the array are stored next to each other in memory, accessing specific indices\footnote{indexes} is simple.
Let us assume that each number in the array is a Java {\mono int} which is a 4 byte wide/32 bit wide integer.
In memory, the array would look as such:

\begin{figure}[htbp]
    \centering
    \begin{tikzpicture}
        \foreach \i/\v/\addr in {0/3/4000,1/4/4004,2/5/4008,3/6/4012} {
            \pgfmathsetmacro\x{\i*2}
            \draw[thick] (\x,0) rectangle (\x+2,1);
            \node[orange] at (\x+1, 0.5) {\monobold{\v}};
            \node[gray,anchor=south west] at (\x,1.1) {\mono \small \addr};
        }
    \end{tikzpicture}
    \caption{the addresses where the integers begin are now labeled.}
    \label{fig:array-memory}
\end{figure}

The locations of the integers in memory follow a \emph{predictable} pattern. Therefore, it is easy to access arbitrary
array indices by simply performing a math calculation. You can simply repeatedly add 4 until you get the nth index you desire,
and add it to where the array begins in memory\footnote{the actual formula is an exercise for the reader}, and ask the computer
to access that index \emph{very cheaply}. One index, one calculation.

The issue with arrays, are that in order to insert new elements, you must create entirely new memory.
This is because all arrays have a fixed and predetermined size. There might be memory after or before the array that is already
in use, which cannot be moved.

Therefore, one could produce a new array and copy all the data from the old memory to it.

    \label{fig:array-extend}

where 7 is the new item to be added.

In Java, this looks as such:

\begin{minted}{java}
int[] array = {3, 4, 5, 6};
// Make a new array with enough space.
int[] new_array = new int[5];

for (int i = 0; i < array.length; i++) {
    new_array[i] = array[i];
}

// we now have space to put the 7 
new_array[4] = 7;
\end{minted}

However, assuming if we had 1000 elements, if we wanted to add a 1001st element, that would require copying 1000 items in memory,
and having 2001 items worth of space reserved in memory until the copy is finished, at which point, Java will automatically clean
up the 1000 items.

Linked lists help us solve this problem.

\subsection{Singly Linked Lists}

\begin{importantbox}
    Every reference to a ``linked list'' will be to a \textbf{singly} linked list.
    If you have not read ahead, it means a linked list that only has pointers in one
    direction; just a ``normal'' linked list if you will.

    If I mention something like a \emph{``doubly linked list''}, this means something
    different, so just assume everything is singly.
\end{importantbox}

Similar to arrays, linked lists allow you to store many pieces of data in a given order in one collection/group.

The idea is quite simple: instead of storing items in a continuous chunk of memory that cannot grow or shrink, linked
lests store data as individual data points, called nodes. Not only do these nodes store the data itself, they also
store the location of where the next item in the linked list is.

This essentially forms the list as a chain, with one item linked to the next one. This means that the list does not have
a fixed size (unlike arrays), and that as long as there is space for another number and a link to the next one (or none)
the list can grow. When there are no numbers to link to ahead, it links to {\mono null}, or address 0, signifiying the
end of the linked list.

This is what it conceptually looks like:

\begin{figure}[htbp]

        \foreach \i in {0,1,3,4,6,7} {

            \pgfmathparse{((\i+1)*\w)+(\w/2)}

            \pgfmathparse{\circlex+1.3}
            \draw [orange,->,line width=1pt] (\circlex,0.5) -- (\circlex+2,0.5);
        }
        \node[orange] at (14.5,0.5) {\monobold null};
    \end{tikzpicture}
    \caption{A simple illustrative diagram of a singly linked list.}
\end{figure}

\begin{importantbox}
    The beginning of a linked list is called the \textbf{head}, and every linked list
    ends with a special value called \textbf{null}. It simply signifies ``nothing'',
    similar to how 0 represents a numerical value of nothing, or an empty set has no
    elements in it.
    \par
    It is present so that code and loops can easily tell when to stop traversing the
    list.
\end{importantbox}

Each of these nodes look like this in Java:

\begin{minted}{java}
// in Node.java
public class Node {
    // for convenience, we make these fields public
    public int data;
    public Node next;

    Node(int data) { 
        this.data = data
        // Set the next to null by default
        this.next = null;
    }
}
\end{minted}

That declared a class {\mono Node} that can be used like any other data type for a variable; it just has
special properties, like being able to hold methods, fields, be assigned to {\mono null} (which has the
special meaning of ``there is no object present here''). You can store it in variables, parameters; anything,
really.

Let's manually create a linked list with the following code:

\begin{minted}{java}
// Create the nodes
Node first = new Node(3);
Node second = new Node(4);
Node third = new Node(5);

first.next = second;
second.next = third;
// third.next is already null
\end{minted}

In memory, the linked list would look like this. Since the nodes were created in succession, they may be placed next to
each other in memory like so:

If you wanted to add a new item to the linked list, you would not need to reallocate anything, instead, you can just
\emph{create another node somewhere else, and point the dot on the node that stores 5 to the new one.}

What makes a linked list a linked list, is the fact that \emph{each piece of data points to the next one, forming a chain, rather
than it being placed next to each other, forming a contiguous chunk.} That reference to the next node makes it linked. Because of
this, you can store more than one piece of data in a node, and the only thing that makes it linked is that reference to
the next node ({\mono Node next} in the class definition).

In exam papers, this situation commonly pops up. In the HL specimen paper 2 (first exam 2027), this Node class showed
up:

\begin{minted}{java}
// Question 6
// ----------
// A computer game stores the name and score of each player in the
// nodes of a linked list.
// 
// The linked list makes use of the Node class, in which the data
// for each node consists of the player’s name and score. This 
// class is shown:
//
class Node {
    public String name;
    public int score;
    public Node next;

    public Node(String n, int s) {
        this.name = n;
        this.score = s;
        this.next = null; // initialize next pointer as null
    }
}
\end{minted}

Which represents a list of player scores.

\subsubsection{The Difference between a Linked List and a Node}

This is a thing that many students get wrong. Linked lists are made up of Nodes. A node is simply a class with any data in it, with some sort of
{\mono next} field that refers to any given ``next'' node. The existence of this next field lets you store the next node in the list, and a chain
of these nodes that refer one after another is a linked list.

\subsection{Operations on Linked Lists}

\subsubsection{Iterating through a Linked List}
\label{sec:linked-list-iteration}

If we ever get a hold of a linked list, we can traverse it, meaning that we go through each item. Just like how we can use
a counter to go over each item of an array and use the data, we can take the node's data, use it and move onto the next node, until
there is no more next node (i.e. when {\mono next == null}).

\subsubsection{Creating a Linked List Manually}

The most naïve way to construct a linked list is to create the nodes separately, and link the next fields manually.

\begin{minted}{java}
public class Demo {
    static Node getNumbers() {
        Node first = new Node(1);
        Node second = new Node(2);
        Node third = new Node(3);
        first.next = second;
        second.next = third;
        third.next = null;
        return first;
    }
    // getNumbers() returns the head of a linked list.aegisfortia maimai
}
\end{minted}

This is very basic, and has no practical purpose, however.

\subsubsection{Adding Nodes to the End of a Linked List}

\begin{importantbox}
The act of adding something to the end of a list (any list for that matter) is called \emph{appending}.
\end{importantbox}

This is one of the more simple tasks you can do with linked lists. The idea is simple; given a linked list of
{\mono String}s like so:

\begin{figure}[htbp]
    \centering
    \begin{tikzpicture}
        \pgfmathsetmacro\w{1.8}
        \foreach \i in {0,1,3,4} {
            \pgfmathsetmacro\x{\i*\w}
            \draw[thick] (\x,0) rectangle (\x+\w,1);
        }
        \foreach \i\n in {0/Apple,3/Orange} {
            \pgfmathparse{(\i*\w)+(\w/2)}
            \node[orange] at (\pgfmathresult,0.5) {\monobold \n};
            \pgfmathparse{((\i+1)*\w)+(\w/2)}
            \pgfmathsetmacro\circlex{\pgfmathresult}
            \fill[orange] (\circlex,0.5) circle (0.05);
            \draw [orange,->,line width=1pt] (\circlex,0.5) -- (\circlex+\w+0.5,0.5);
        }
        % this value is just eyeballed lol
        \node[orange] at (11.3,0.5) {\monobold null};

        \draw[gray,thick,->] (0.6, -0.6) -| (0,-0.1);
        \node[gray,anchor=west] at (0.7, -0.6) {\mono \small \emph{head}};
    \end{tikzpicture}
\end{figure}

And given that the node is defined as such:

\begin{minted}{java}
class Node {
    String item;
    Node next;

    Node(String s) {
        this.item = s;
    }
}
\end{minted}

And given that \emph{head} is a method defined as such:

\begin{minted}{java}
static void appendNewItem(Node head, String newItem) {
    // ...
}
\end{minted}

How does one complete the method, append to the end of the list list referred to by head?

The simple answer would just be to access the Node containing ``Orange'', and then setting it's value
of {\mono next} to whatever the new item is. If you wanted to cheat, you could just do this:

\begin{minted}{java}
static void appendNewItem(Node head, String newItem) {
    head.next.next = new Node(newItem);
    // ^^^ bad! ^^^
}
\end{minted}

But this would kind of \emph{assume} that the list is only 2 items long, and in computer science, we 
want to \emph{generalize} as much of our work as possible. \emph{How do you append an item to the end of any
given list?}

One could generalize this to two steps:\footnote{This is just how I like to think about it}

\begin{enumerate}
    \item Somehow get a hold of the last node of the list.
    \item Assign its next to a new node containing your data.
\end{enumerate}

The first step you have already learned in \ref{sec:linked-list-iteration}, which looks something like this:

\begin{minted}{java}
static void appendNewItem(Node head, String newItem) {
    Node current = head;
    while (current != null) {
        // no need to do anything with the data, just move on
        current = current.next;
    }
    // Should be the last valid node, right?
    current.next = new Node(newItem); 
}
\end{minted}

But notice a problem? \emph{on line 7, the value of current is null.} This is because our loop terminated when
current became null, meaning that this happened on the last iteration:

\begin{enumerate}
    \item Current is not null, so we do {\mono current = current.next}
    \item On the next iteration on line 3, {\mono current} is null. Stop.
\end{enumerate}
